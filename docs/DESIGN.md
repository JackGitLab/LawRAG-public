# LawRAG 设计决策与取舍

> 文中阶段报告与完整错误档案属于历史过程材料，原件保留本地；当前成果及固定历史链接见 [RESULTS](RESULTS.md)，精选复盘见 [ENGINEERING_NOTES](ENGINEERING_NOTES.md)。

本文记录 MVP 已采用的方案、选择原因和明确放弃的复杂度。运行方式与效果概览见项目根目录的 [README](../README.md)，错误事件与预防措施见 ERRORS.md（未公开的历史记录）。

## 1. 检索、向量化与生成服务分工

**选择：** 使用 LlamaIndex 负责文档加载、节点组织、索引和检索；通过 SiliconFlow 调用 `BAAI/bge-m3` 生成 1024 维文本向量；使用 DeepSeek `deepseek-chat` 根据检索资料生成回答。

**原因：** LlamaIndex 提供了当前 MVP 所需的文档到检索链路，`BAAI/bge-m3` 对中文语义检索友好，DeepSeek 负责生成时可通过兼容接口直接调用。DeepSeek 没有 embedding 接口，因此向量化必须由第三方服务承担。入库与查询共同读取同一向量模型配置，避免向量空间不一致。

**放弃了什么：** 没有为生成和向量化强行统一供应商，也没有引入额外模型网关或配置框架。代价是系统依赖两个外部 API，但职责边界清晰。

## 2. Chroma 持久化向量索引

**选择：** 使用 Chroma 将索引持久化到本地 `chroma_db/`，文档更新时运行一次入库，问答时直接加载已有集合。

**原因：** 当前语料规模小，Chroma 能以较少代码提供持久化、元数据和相似度检索，不需要单独部署数据库服务。持久化还避免了每次提问都重新解析文档和调用批量向量化。

**放弃了什么：** 没有使用只存在于进程内的内存索引，因为它会在每次启动后重建；也没有采用面向生产集群的独立向量数据库，因为部署、鉴权和运维成本超出 MVP 范围。

## 3. 法条按“条”切块

**选择：** 清理 DOCX/TXT 的多余空行、全角空格、章节标题和页码残留后，以“第X条”为边界切块，每条法条形成一个完整节点。

**原因：** 法条是引用和解释的最小稳定语义单元。保持完整条文可以让检索结果直接对应法条编号，也能避免款项、条件或例外被固定长度切分截断。

**放弃了什么：** 没有采用固定字符数或 token 数切分。固定长度实现更通用，但可能把同一法条拦腰截断，或者把相邻法条混在同一个块中，降低引用准确性。

## 4. 多轮编排、工具路由与 MCP 客户端能力

**选择：** 保留 `POST /api/ask` 单轮链路，同时为多轮链路使用 LangGraph，按 `prepare → retrieve → route → (tools) → generate` 编排追问改写、top3 检索、工具路由与回答生成；外部搜索通过 MCP client 接入，但 LawRAG 本身仍不暴露为 MCP server。

**原因：** LangGraph 的消息状态与 SQLite Checkpointer 保存轮次历史，并把追问改写、检索、路由和工具调用设为可观察节点。MCP 只用于第三方外部服务边界，使协议能力与业务工具保持分离。

**放弃了什么：** 没有扩展为自由规划的代理或循环式工具调用，也没有把 LawRAG 暴露为 MCP server；每轮最多调用一轮工具，避免把可解释的问答链路扩大成开放式代理。

## 5. 检索质量与已知瓶颈

**选择：** 用 [55 道固定回归问题](../tests/regression_questions.json)持续度量 top3 召回，并区分 20 道口语化库内题、25 道术语直问库内题与 10 道库外拒答题。

**原因：** 固定问题集能把“感觉能用”转化为可复现指标。当前默认混合召回加重排策略在 55 题修订版最终基线中的 top3 命中率为 **100.0%（45/45）**；未改动的 10 道库外题最近一次拒答验证通过率为 **100.0%（10/10）**。

**放弃了什么：** 除经复核后为第 31、35 题补充多法条期望值外，没有为了提高指标改写其他题目、期望值或判定逻辑。扩充后的题集更难，与早期 20 题版本不属于同一评估口径。

## 6. DOCX 语料与 Git 二进制属性

**选择：** 保留来自法律法规数据库的 `.docx` 原始语料，由 LlamaIndex 文件读取器直接解析；在 `.gitattributes` 中声明 `*.docx binary`。

**原因：** 保留 DOCX 避免人为转写法律文本，同时满足直接解析源文档的目标。二进制属性阻止 Git for Windows 继承全局 DOCX textconv 规则，避免历史 diff 依赖本机不存在的外部命令。

**放弃了什么：** 没有把 DOCX 预转换为仓库内的纯文本副本，因为这会引入双份内容及同步责任；代价是二进制文件无法获得逐行 diff。故障根因和修复证据见 E-003（未公开的历史记录）。

## 7. 安全事件 E-001 的机制性修正

**选择：** 密钥只从系统环境变量读取；验证配置时只运行安全自检脚本，脚本只报告变量名和读取状态；禁止通过配置界面截图或会回显变量值的命令证明配置成功。

**原因：** 配置存在性可以在不展示凭据的情况下验证。将检查方式固化到代码和项目约定，比依赖操作者临时判断更可靠。

**放弃了什么：** 不使用仓库内 `.env` 保存凭据，也不把密钥值写入错误档案、README、测试或 CI。事件经过与完整预防措施见 E-001（未公开的历史记录）。

## 8. 检索方案评估

### 问题与候选方案

第 15 题“商家贴着‘售出概不退换’，这句话一定有效吗？”在纯向量 top3 中未命中消保法第二十六条。诊断时第二十六条实际排第 4，相关度为 0.6454；第 3 名为 0.6459，分差仅 0.0005。这说明目标条文已经被召回，但被 top3 截断，首先应处理排序，而不是修改题目。

早期曾以第 15 题的口语表达与目标条文字面不重叠为由排除混合检索。这个判断以单个极端案例否定整体方案，不足以量化 BM25 的实际贡献。法律条文和用户问题中仍有大量稳定专有名词，例如“试用期”“经济补偿”“竞业限制”“七日无理由退货”，它们正是关键词检索可能擅长的信号，因此本轮补测 BM25 及两种混合方案。

- **vector：** 直接用原问题向量检索 top3。调用少、速度快，但口语表达与法条措辞存在差异时容易漏检。
- **vector_rerank：** 先向量召回 10 条，再用 `BAAI/bge-reranker-v2-m3` 按原问题重排并取 top3。它增加一次重排请求，但不需要额外生成文本。
- **hyde：** DeepSeek 先生成不超过 120 个汉字的假想条文式检索文本，用它向量召回，再按原问题重排。语义桥接能力更强，但每题增加一次短生成，带来成本、延迟和输出波动。
- **multi_query：** DeepSeek 生成 3 个不超过 40 个汉字的改写查询，与原问题并行召回，用 RRF 合并候选后重排。它能覆盖更多表达方式，但一次问题需要四路向量查询，链路最复杂。
- **bm25：** 从当前 Chroma 集合读取同一批法条节点，用 jieba 分词和 Okapi BM25 建立进程内关键词索引，直接返回 top3。它不调用外部服务，用于独立量化关键词检索的贡献。
- **hybrid：** 向量与 BM25 各召回 10 条，用 RRF 融合后直接取 top3，不调用重排。它同时覆盖语义和字面信号，但两个召回器的弱结果也可能进入最终排序。
- **hybrid_rerank：** 向量与 BM25 各召回 10 条，经 RRF 合并候选后，再用现有 reranker 取 top3。外部调用形态与 `vector_rerank` 相同，但多一个本地 BM25 召回源。

### 实测结果

本节记录 **最终基线（55 题修订版）**：45 道库内题用于命中率，其中 A 组为 20 道 `colloquial` 口语化/场景化问题，B 组为 25 道 `terminology` 法条术语直问；10 道 `out_of_scope` 空 expect 题不参与命中率。第 31 题现在同时接受消保法第十八、四十八条，第 35 题同时接受第八、二十条；其余 53 题未改。由于题数或判定口径不同，本基线与 45 题版、55 题未修订版均不可直接比较。

最终命中结果采用增量重建：沿用上一轮完整 55 题实测中其余 53 题的命中状态和平均耗时，只对判定标准变化的第 31、35 题重跑七个策略，共 14 次检索，并用新结果替换旧记录。两题在七个策略下均命中新 expect 中的至少一条。检索模型、算法和其他题目均未改变，因此无需重跑其余 53 题；表中耗时仍是上一轮完整遍历 55 题的端到端均值。HyDE 与 Multi-query 只生成检索辅助短文本，不调用最终法律回答生成。

### 最终选择与取舍

**测试集偏差。** 纯 BM25 在 A 组为 55.0%，在 B 组达到 92.0%，相差 37 个百分点，证明口语化题占主导会系统性压低关键词检索的总体表现。评估检索策略时必须同时报告提问风格分布和分组结果，否则总体命中率会把样本构成误当成算法能力。不过 BM25 在 B 组仍低于 vector 的 100.0%，没有反超；第 6、49 题即使包含法律术语，纯关键词排序仍未进入 top3。向量检索在本语料上同时覆盖了术语直问和多数语义改写。

**rerank 并非总是改善排序。** 第 35 题中，纯 vector 的 top3 同时包含消保法第八、二十条，而 `vector_rerank` 将第二十条挤出 top3，只保留第八条。这说明交叉编码器会发生误判，不能把“增加重排”当成逐条单调改进；修订后的多答案口径使两者都算命中，但排序损失仍客观存在。总体上重排使 vector 从 42/45 提升到 44/45，仍须结合逐题结果观察被救回和被损失的法条。

**最终选择：`hybrid_rerank`。** 证据链从第 15 题开始：纯 vector 已将目标第二十六条召回到第 4，仅因 top3 截断失败，说明需要改善排序；随后 45 题版七策略对比中，`hybrid_rerank` 以 33/35 高于 `vector_rerank` 的 32/35，并救回第 30 题；55 题公平赛道未修订版中，它以 43/45 对 42/45，A 组 90.0% 对 85.0%、B 组同为 100.0%，证明增益不依赖术语题偏置；最终修订第 31、35 题的多答案口径后，它达到 45/45，A/B 均为 100.0%。它不增加 LLM 调用，完整 55 题实测平均耗时仅比旧默认增加 392.4 ms（约 8.8%），因此默认策略正式从 `vector_rerank` 切换为 `hybrid_rerank`。

不接重排的 `hybrid` 为 88.9%（40/45），A、B 两组都低于旧默认 `vector_rerank`，说明简单 RRF 会把 BM25 的弱排序带进 top3，重排是混合检索取得净增益的关键。HyDE 与 Multi-query 同为 100.0%，分组结果也与 `hybrid_rerank` 相同，但平均耗时分别为 7295.7 ms 和 10350.9 ms，还增加生成调用或向量调用及外部故障面，不取代默认方案。

### 评估集标注说明

上一轮先补充题型和术语样本、不修改既有 expect，用于单独观察测试集分布偏差；本轮再修订第 31、35 题，避免把两种变化混在同一基线中。第 31 题同时接受第十八条的安全保障义务与第四十八条的侵权责任；第 35 题同时接受第八条的消费者知情权与第二十条的经营者如实说明义务。命中判定仍是任一 expect 进入 top3 即算命中。

口径修订使各策略分别增加一至两个命中，但不代表检索算法发生改善；因此最终基线必须明确称为“55 题修订版”，不能与 45 题版或 55 题未修订版直接比较。

## 9. HTTP 服务与演示页面封装

### 接口形态

**选择：** 使用 FastAPI 保留无状态的 `POST /api/ask`，并提供 `POST /api/chat`、`GET /api/sessions`、`GET /api/sessions/{session_id}` 作为多轮会话接口；显式 `GET /` 在构建产物存在时返回 Vue 入口文件，不存在时返回 404；`GET /minimal` 返回免构建的极简页。应用仅在启动时确认 `frontend/dist/` 存在的情况下注册静态资源挂载。

**原因：** `/api/ask` 继续提供最小单轮回归入口，`/api/chat` 则让 Vue 页面在首次提问时自动创建会话，并用响应中的 `session_id` 延续追问。结构化引用仍由当前轮响应返回，会话详情只公开 user/assistant 消息。

**取舍：** 当前加入本地 SQLite、LangGraph 多轮状态、SSE 流式输出与 MCP 客户端及服务端能力，不加入鉴权、容器或部署配置。会话 ID 只保存在前端内存中，刷新页面不会自动恢复当前会话；用户可从服务端会话列表重新选择历史会话，这仍避免引入账户和浏览器持久化边界。

### 多轮状态与持久化分工

编排图为 `prepare → retrieve → route → (clarify | tools → generate | generate)`：`prepare` 在首轮直接使用问题，在已有历史时把追问改写为可独立检索的问题；`retrieve` 沿用现有检索策略返回 top3 法条；`route` 决定进入 `clarify`、`tools` 还是 `generate`；`generate` 结合检索资料与可选工具资料生成回答。图状态在原字段之外增加 `planned_tool_calls`、`web_sources` 与 `tool_text`，其中消息仍只通过 `prepare` 与 `generate` 写入，路由和工具节点不污染会话历史。计算缺参追问再增加 `calc_context`（进行中的计算任务及其状态），并新增 `clarify` 节点承担缺参追问与更正确认。

### 工具层与混合路由

1. **本地工具与 MCP 的边界：** 法定赔偿/补偿计算是进程内、确定性且无外部 I/O 的业务函数，直接包装为 LangChain tool；法规时效核验和联网搜索依赖第三方博查服务，才通过薄 MCP stdio server 接入。在自己的进程里为本地计算器启动 MCP server 再连回来只会增加序列化和进程开销，是反模式。
2. **外部工具由用户显式开启：** 输入框旁的“联网搜索”开关随每轮请求传入，默认关闭；关闭时不调用联网搜索或法规时效核验。开启后，“修订、废止、现行有效”等时效问题把完整问题交给法规时效核验，其余问题调用通用联网搜索。联网工具有成本、延迟且结果不可复现，因此是否允许联网由用户决定，模型不参与该决策；确定性分流仍保住调用路径的可解释性。
3. **模型兜底只负责计算器抽参：** 只有命中计算类关键词时才调用路由模型，并且模型只绑定进程内的本地计算器。模型抽出的月工资或工作年限缺失、为零或为负时直接丢弃调用；未命中任何规则时不调用模型。由此“要不要调外部工具”完全确定，只有“计算器参数怎么填”依赖模型。无工具时 `build_prompt_with_tools()` 逐字回退到既有 `build_prompt()`，保住 55 题基线口径。
4. **计算器拒绝假结果：** 本地计算器对非正数月工资或工作年限直接返回缺参说明，文本不包含最终金额，不产生 `0.00 元` 这类由无效参数造成的假答案。
5. **联网核验资料的最低可用形态：** 外部搜索工具返回的结果可能不含摘要正文（实测博查在部分额度下 `summary` 为空），此时资料只剩来源标题、站点与日期。这类“标题级”结果仍被写入提示词的“检索资料”段，并在提示词中显式声明其属于可用资料、要求据此给出明确结论并注明来源，从而避免模型以“资料未涵盖修订历史”为由整段拒答；检索失败或额度不足仍如实说明，不编造。
6. **为什么只跑一轮工具：** 当前三个工具都用于补充一次性事实或确定性计算，不需要工具之间反复规划。固定一轮能让调用路径、成本和失败降级清楚可讲，也避免引入 ToolMessage 配对和开放式代理循环。
7. **为什么保持同步图：** 当前 `SqliteSaver` 的异步方法实测抛出 `NotImplementedError: The SqliteSaver does not support async methods. Consider using AsyncSqliteSaver instead.`。因此图继续同步执行，节点通过 `asyncio.run` 桥接 async-only 的 MCP 工具；如果调用线程已存在事件循环，则在独立线程内运行桥接。调用图的 HTTP 端点必须保持同步 `def`，不能改成异步端点后直接复用这条路径。
8. **MCP 的诚实取舍：** 单机场景下 MCP 没有性能收益；当前实测每次工具调用会新起一个 stdio 子进程，端到端约 4 秒。采用它是为了展示协议边界、外部工具接入与未来多服务扩展能力，而不是声称它比进程内调用更快。
9. **计算器缺参追问（第二阶段，含返工 R1、R2、R3）：** 参数不齐时不再静默丢弃计算调用，而是把任务存进会话状态并在本轮输出确定性追问。选择这样做是因为“缺参时只回答一句无法计算”既不保存已确认参数，也不告诉用户还缺什么。实现要点：
   - **参数来源逐字段核验：** 计算参数只从用户原话 `state["question"]` 抽取（被追问改写模型加工过的 `search_query` 不参与抽参），随后用一个受限字面量扫描器把原话里的数字按**当前片段与字段词含义**归属。归属先按**单位优先**：紧跟 `年/个月` 的数值只作年限，带 `元/块/万` 的数值只作金额，二者不会同时成立；金额再按**片段内字段词**分流——`赔偿/退款/补偿金/金额` 等其他金额**不作为任何工资依据**，`社平/职工月平均/上年度职工` 归当地社平工资（该称谓常含“工资”，按完整字段含义优先于个人工资），`工资/月薪` 归个人月工资，带“元/万”但无字段线索的金额只在字段含义唯一时可用。字段词只看**当前片段**（以 `，,；;。.！!？?、换行` 为硬边界），因此已结束片段的“社平”不会越界覆盖下一片段的“赔偿/月工资”，社平与个人月工资的先后顺序也不改变各自归属。模型返回的每个数值必须与本轮的对应依据一致才会被采用或作废。**放弃了什么：** 不做通用表单/槽位框架，不做通用中文数字解析——只支持阿拉伯数字与常用中文数词（含“半”）；复合年限“N年M个月”一律阻断并要求用统一年数确认，小写/大写金额同样继续追问而不猜测；无法确定归属时追问而非猜测。
   - **原话可证的更正优先于模型输出：** 明确取消与显式新任务在调用模型之前处理；原话可证的无效更正（零/负数）与复合年限也在调用模型之前让对应字段失效，因此模型返回空调用、仅 `kind`、漏报该字段或回带旧值都不会让失效值复活。每轮另有一个 `reply` 标记（`ask` / `correction_ack` / 空）决定本轮是追问、更正确认还是普通问答。
   - **任务生命周期与执行边界：** 状态为 `awaiting / computing / done / failed`，`route` 只写 `computing`，`call_tools` 在计算器真正返回后才写 `done`、抛错写 `failed` 并保留上下文供明确重试。
   - **统一分流：** 本轮没有可采用的新字段值时，空调用、仅 `kind`、无依据的历史参数走同一条判断——字段相关澄清保留任务并正常回答、无法归属的金额追问、换话题结束任务。
   - **代价：** 追问不经过生成模型、追问轮不执行本轮其他已规划工具、追问轮清空检索引用（避免引用与实际回答不一致）。不支持同一会话内多个并行待办计算任务；`kind` 仍由路由模型依情形判断，只在追问文案与工具输出的前提说明里显式标注假设。限制与未验证项见 [STAGE2_CLARIFICATION.md](STAGE2_CLARIFICATION.md)，相关错误见 ERRORS.md（未公开的历史记录） 的 E-092～E-094 与 E-038 复发记录。

SQLite 中的 `sessions` 表只保存 `id`、标题和创建/更新时间，用于会话列表与存在性校验；完整消息历史由 LangGraph SQLite Checkpointer 保存，避免在业务表重复维护同一份消息。每轮新生成的助手消息把对应引用以纯字典写入 `AIMessage.additional_kwargs`，因此重新打开会话时仍能展示该轮来源；改造前的历史数据没有逐轮引用，只能为最后一轮兼容读取 checkpoint 当前 citations。HTTP、前端和业务数据库统一使用 `session_id`；仅在 Checkpointer 边界由 `graph_config()` 映射为外部库要求的 `thread_id`，所有 `invoke()` 与 `get_state()` 都使用这一唯一映射点。

### 对外暴露 MCP server（工具提供方）

LawRAG 同时承担 MCP 消费侧与提供侧：它作为 MCP client 调用仓库内的博查薄 server，也把自身 FastAPI 能力作为 MCP server 对外提供。提供侧只白名单暴露 `ask_law_question`、`chat_law_question`、`list_sessions`、`get_session`、`delete_session` 五个 operationId；`POST /api/chat/stream` 是 SSE 长连接，`GET /` 与 `GET /minimal` 是静态页，因此不作为工具暴露。

`FastApiMCP` 必须在所有业务路由定义完成后构造，才能读取完整 OpenAPI；`mount_http()` 必须先于 `StaticFiles` 挂载，否则 `/mcp` 会被根路径静态挂载遮蔽。工具调用通过进程内 `ASGITransport` 直连同一 FastAPI 应用，不额外开放端口。session manager 在首个请求时懒启动，因此不接管或修改既有 `lifespan`。`delete_session` 是破坏性操作，本阶段为演示完整性一并暴露；生产环境应增加鉴权。

### 流式输出与会话管理

1. **为什么使用 SSE 而非 WebSocket：** 当前交互只有服务端向浏览器持续发送生成 token，提问仍是一次普通 POST，不需要全双工长连接。SSE 可以沿用 HTTP、同源代理与现有错误边界，前端用原生流读取即可，无需新增协议层或依赖。
2. **为什么使用 `stream_mode="messages"` 并同时按节点与消息类型过滤：** 真实库会把节点内普通 `.invoke()` 自动转换为消息 chunk，因此无需把模型调用改成 `.stream()` 或设置 `streaming=True`。`prepare` 节点的消息也会发射，后端必须先限定 `metadata["langgraph_node"] == "generate"`；generate 节点返回的整条 `AIMessage` 还会使用新 id 再发射一次，绕过按 id 去重，因此必须再限定只接受 `AIMessageChunk`，同时跳过空 chunk，才能避免改写文本和重复完整回答混入 token 流。
3. **为什么另开 `/api/chat/stream`：** 既有 `/api/chat` 继续维持单个 JSON 响应及原有回归测试，新端点单独定义 `session → token → done/error` 的 SSE 契约。这样非流式调用方无需迁移，也不会因响应首部提前发送而改变原有 HTTP 错误码语义。
4. **为什么删除会话需要双写清理：** `sessions` 表只负责标题与时间等列表元数据，Checkpointer 独立保存消息线程。删除端点先调用 `delete_thread(session_id)` 清除消息状态，再删除 `sessions` 行，避免列表消失但历史数据仍留在 checkpoint。
5. **停止生成的行为与代价：** 真实验收在收到第 3 个 token 后由客户端关闭响应，等待 3 秒再读取会话，Checkpointer 中只有 1 条 `user` 消息，没有 assistant 消息，最后一条 assistant 内容长度为 0。前端会保留断开前已经显示的局部文字，但这部分不会作为助手消息持久化；切换会话或刷新后只能恢复用户问题。该行为避免把不完整回答写进历史，代价是用户看到的部分生成内容无法恢复。
6. **为什么只在呈现层兼容 citation 形态：** checkpoint 回放后 `NodeWithScore.node` 会退化为 dict，第二轮实测 values 帧中的节点形态依次为 `['dict', 'dict', 'TextNode', 'TextNode']`。本轮让 `_citation_fields()` 同时读取活对象与字典节点，没有把 ChatState 中的 citations 改成纯字典；后者会牵动 `retrieve()`、`run_turn()`、`/api/chat`、既有断言及状态迁移测试，超出本阶段收尾范围。该取舍对应 E-032（未公开的历史记录） 的已知序列化边界。
7. **为什么前端按会话维护独立流任务：** 单一全局 loading/controller 会阻止生成期间创建新会话，也可能让后台 token 写入用户刚切换到的消息列表。前端现在为每个会话保存独立控制器、等待状态和消息数组；切换或新建只改变当前视图，已有 SSE 继续更新自己的缓存。“停止”只终止当前查看会话的流，同一会话仍限制为一次生成，避免并发写入同一 Checkpointer 线程。

### 前端工程化

**为什么引入 Vue：** 原生 `app/static/index.html` 已验证接口和最小交互；阶段 B 引入 Vue 3 与 Vite，把依赖、开发服务器、构建入口和响应式页面状态纳入明确的前端工程结构，为后续页面演进提供稳定入口。阶段 C 仍保持单页应用，只把重复的消息与引用展示拆为一个小组件，不引入路由或状态管理库。

**为什么不用 TypeScript 和 UI 组件库：** 当前数据结构只有问题、回答和引用，原生 JavaScript 与 scoped CSS 足够清楚。TypeScript 配置、组件库依赖和主题体系暂时不会带来与复杂度相称的收益。

**为什么默认入口归 Vue：** 项目作为求职作品集，外部使用者 clone 后沿 README 的单一路径即可看到工程化页面，比默认展示内部验证用的极简页更符合当前目标。显式根路由返回 `frontend/dist/index.html`，所有其他显式路由之后的静态挂载负责 `/assets/*` 等构建资源，避免遮蔽 API 与接口文档。

**为什么极简页移到 `/minimal` 而不删除：** `app/static/index.html` 已验证最小问答链路，且在没有 Node.js 或尚未构建前端时仍可用于排错。保留原文件并改由 `/minimal` 提供，可以维持这一低依赖入口而不与 Vue 默认入口竞争。

**为什么 `dist/` 不入库：** 构建产物可以由锁定的前端依赖和源码重复生成，提交它会造成源码与产物双份 diff 及同步责任。代价是全新 clone 后必须先执行前端构建；未构建时 `/` 和静态资源请求返回 404，但后端、API、`/minimal` 与测试仍能启动。

**为什么放弃 `check_dir=False`：** Starlette 的该参数只跳过 `StaticFiles` 初始化阶段的目录检查；请求期 `check_config()` 遇到目录缺失时仍无条件抛出 `RuntimeError`。失败路径不会把 `config_checked` 置为真，后续对 `/`、`/favicon.ico` 或 `/assets/*` 的每次请求都会再次抛错并返回 500。因此它既不能实现未构建时的 404，也会掩盖挂载时的真实配置前提。

**为什么使用显式根路由和条件挂载：** 根路由直接检查 `frontend/dist/index.html`，使未构建时的 `/` 稳定返回带操作提示的 404；应用只在启动时确认 `frontend/dist/` 存在后注册 `StaticFiles`，使未构建时 `/assets/*` 与 `/favicon.ico` 由 FastAPI 正常返回 404，不会进入 Starlette 的目录校验异常。此时不会回退到极简页；需要低依赖页面时应明确访问 `/minimal`。由于挂载决策只在进程创建应用时执行，构建完成后必须重启已运行的后端进程。

**为什么单端口下不需要 CORS：** 生产模式中 Vue 页面与 `/api/ask` 都由同一个 FastAPI 来源提供，浏览器请求同源。开发模式仍由 Vite proxy 转发 `/api`，两种模式都不需要放宽后端 CORS 策略。

**为什么开发期使用 Vite proxy：** 浏览器只请求 Vite 的同源 `/api`，由开发服务器转发到本机 FastAPI。这样无需仅为本地双端口开发而放宽后端 CORS 策略；代理边界集中在 `vite.config.js`，与生产模式的同源挂载互不干扰。

### 资源生命周期

**选择：** embedding 客户端与 DeepSeek 客户端继续使用 `app.config` 中的 `@lru_cache` 单例；Chroma `VectorStoreIndex` 和 BM25 索引也分别由 `load_index()`、`get_bm25_index()` 进程内缓存。FastAPI lifespan 在应用启动时校验两个既有环境变量，先加载向量索引，再构建 BM25 索引。请求处理函数只调用现有问答入口，不创建客户端或重建索引。

**原因：** 同一服务进程内的多个请求应复用向量索引、BM25 索引和客户端，避免重复打开 Chroma、重复分词整份语料、重复构造索引包装和重复创建 HTTP 客户端。lifespan 使配置错误在接收流量前暴露，也让资源初始化顺序和单次预热边界可测试。

**错误边界：** 缺少环境变量时应用启动失败，提示具体缺失的变量名但不显示任何值；索引未入库时页面仍可打开，问答接口返回 503 并提示先执行入库；输入错误由 Pydantic 返回 422；向量化、重排或生成服务失败时返回不含内部细节的 502，完整堆栈写入 `logs/`。

## 10. 后续演进方向

以下方向已经评估，但不属于本次服务化范围。

### 10.1 图增强（GraphRAG 及其轻量替代）

- **是什么：** 完整 GraphRAG 通过实体、关系和社区摘要支持全局综述类问题及多跳关系推理。轻量替代方案是只抽取法条之间的明确引用关系，例如第四十六条引用第四十四条，在检索命中后扩展一跳邻居。
- **为什么现在不做：** 当前知识库只有两部法律，主要是“问题对应哪条法条”的点查询；完整建图、抽取、存储和图检索的成本与当前收益不匹配。
- **什么条件下值得做：** 当语料扩展后出现大量跨条、跨法引用问题，或回归证据表明单点检索经常遗漏必要引用链时，优先试验一跳法条引用扩展。它可能补全引用链，并减少无关条文占用 top3 的机会；只有轻量方案仍不能覆盖全局综述或多跳问题时，再评估完整 GraphRAG。

### 10.2 评估集标注口径修订（已完成）

- 第 31、35 题已采用多法条期望值，并已按修订后的统一口径更新最终基线。本项不再作为待办继续扩展，以免在冻结前持续改变判定标准。

### 10.3 HyDE 设为可选策略

- **是什么：** 先由 DeepSeek 生成简短的假想条文式检索文本，再进行向量召回和重排。最终基线中 top3 命中率为 100.0%，与默认 `hybrid_rerank` 相同。
- **为什么现在不做：** 完整 55 题平均耗时为 7295.7 ms，高于默认方案的 4836.7 ms，并多一次生成调用及相应的成本、波动和故障面；没有取得额外命中收益。
- **什么条件下值得做：** 当出现明确的质量优先场景，且调用方接受更高延迟与成本时，可将 HyDE 作为显式可选策略开放，但不替换当前默认值。

### 10.4 扩充法律语料

- **是什么：** 在现有《劳动合同法》和《消费者权益保护法》之外加入更多法律、法规或司法解释。
- **为什么现在不做：** 当前阶段验证的是既有两部法律上的检索、生成与服务封装；直接扩充会同时改变索引规模、问题覆盖范围和质量口径。
- **什么条件下值得做：** 当确定下一批目标领域和权威语料来源后再扩充。每次扩充都必须重新入库、补充或分层维护回归问题，并重跑评估以建立新的质量基线。

### 10.5 测试集可信度改进

#### 明确当前基线的边界

- **是什么：** 明确 45 道计分题为自建题、样本偏小，且期望值曾在优化过程中修订，存在“出题、改标准、判分同一方”的自我认证风险。当前 100% 仅表示在这 45 题与修订后口径下的 top3 命中率，不等于系统准确率，也不覆盖回答质量。
- **为什么现在不做：** 本阶段只进行前端工程化，不重新设计或执行评估流程；直接扩大指标含义反而会掩盖现有证据边界。
- **什么条件下值得做：** 对外报告、比较新策略或准备发布系统质量结论前，应把这组限制作为指标解释的固定组成部分。

#### 扩充至 100 题以上并增加来源多样性

- **是什么：** 将计分题扩充到至少 100 题，并尽量从不同人员、真实咨询表达和独立资料中采样，而不是只由同一开发过程生成。
- **为什么现在不做：** 高质量扩题需要来源整理、去重、法律复核和分层设计，不能在前端阶段用批量生成题目替代。
- **什么条件下值得做：** 有稳定的复核人力、可追溯题目来源，并准备建立下一版独立基线时实施。

#### 冻结测试集

- **是什么：** 发布一个固定版本，此后不再修改其期望值；发现争议题时记录问题并进入下一版本，使后续优化可以在不移动标准的情况下独立验证。
- **为什么现在不做：** 当前题集刚完成第 31、35 题口径修订，还缺少独立复核和正式版本化规则。
- **什么条件下值得做：** 完成全量人工复核、消除已知歧义并记录版本后，冻结该版本并将新题或标准变化放入下一版。

#### 增加端到端回答质量评估

- **是什么：** 通过人工抽查或模型评分评估完整回答，覆盖是否编造、引用是否恰当、结论是否受材料支持等 top3 命中率无法反映的维度。
- **为什么现在不做：** 需要先确定评分量表、抽样方式和复核机制；当前只有检索层的稳定基线，仓促引入模型裁判会增加另一层未经校准的偏差。
- **什么条件下值得做：** 回答质量成为发布门槛，且已有明确评分标准、盲评流程和争议复核机制时加入持续评估。

#### 增加对抗性题目

- **是什么：** 加入“试用期”与“服务期”等易混术语、相近权利义务和否定式提问，检验系统是否真正区分概念而非只匹配关键词。
- **为什么现在不做：** 对抗题需要系统性梳理易混概念并由法律知识复核，临时添加少量例子不足以形成可信结论。
- **什么条件下值得做：** 扩充测试集时已经建立易混概念清单，并能为每题提供明确依据和错误类型标签时实施。

### 10.6 公网部署

- **是什么：** 把前端、FastAPI 服务和索引部署到可公开访问的运行环境，为作品集提供无需本地安装的演示地址。
- **为什么现在不做：** DeepSeek 与 SiliconFlow API key 必须保存在服务器端，公开入口意味着任何访问者都可能消耗真实额度。当前尚未设计请求配额、身份限制、速率控制和成本告警，直接公开会形成不可控的费用与滥用风险。
- **什么条件下值得做：** 已确定可承受的演示配额，并实现服务端限流、滥用防护、成本监控和密钥轮换后，再选择托管环境并公开演示地址。
